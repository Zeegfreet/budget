# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product overview

Budget is a **personal finance management SaaS**. Core requirements that shape every feature:

- **Strict per-user isolation (multi-tenant)**: each user can only see and change their own finances. Every query for user-owned data must be scoped to the authenticated user (or to a group they belong to). Never trust an owner/user id sent in the request body or params; derive it from the auth context. Cross-tenant access must return `404` (not `403`) so resource existence isn't leaked, and e2e tests must cover "user A cannot read/update/delete user B's data".
- **Finance groups (shared finances)**: besides personal finances, a user can create a group (e.g. a shared house/"república") that has its own incomes and expenses (e.g. rent). Group data is visible only to its members.
- **Invitations**: a group member invites another user to join; the invitee must accept before gaining access. Membership can end (leave/removal), which revokes access.
- **Split methods**: a group defines methods for dividing its incomes/expenses among its members (e.g. equal split, fixed amounts, percentages/weights). Each group income/expense uses a split method, and the resulting shares per member must add up to the total.

Money values should be stored as integer minor units (cents) or decimals, never floats, so splits and totals stay exact.

## Definition of done: tests and CI/CD are mandatory

Every resource/feature we create (API module, endpoint, frontend page/component, etc.) is only complete when it ships with:

1. **End-to-end tests (top priority)** covering the real usage flows of the feature, not just the happy path: success cases, validation errors (the global `ValidationPipe` rejects unknown/invalid fields), not-found, and other relevant error responses.
   - API: `apps/api/test/<feature>.e2e-spec.ts`, run with `pnpm test:e2e`, booting the real `AppModule` via Supertest against an isolated test database (never `dev.db`).
   - Web: user-flow tests for each screen with Vitest + Testing Library, rendering the real route tree via `renderRoute(path)` from `src/test/render.tsx` and mocking the feature's `api.ts` (see `src/routes/index.spec.tsx`).
2. **Unit tests** (`*.spec.ts` next to the source) for services, controllers and non-trivial logic, mocking `PrismaService` where needed.
3. **CI/CD coverage**: the CI pipeline (`.github/workflows/ci.yml`) runs lint, build, unit tests and e2e tests for every app on each push/PR. When a feature needs a new step (migrations, env vars, seed data, a new app/package), update the workflow in the same change. The `api` job generates the Prisma client and runs e2e against `DATABASE_URL=file:./test.db` after `prisma migrate deploy`; the `web` job generates the route tree, then lints, tests and builds.

4. **README update**: the root `README.md` (written in Portuguese) must reflect the change in the same task: update the "Status dos recursos" table, and the stack, setup, env vars, testing, CI/CD or deploy sections whenever the feature touches them (e.g. new env var, new dependency/service, Docker files, deploy steps).

Don't consider a task done, or open a PR, while tests are missing or failing.

## API architecture

- **ESM + nodenext resolution**: all relative imports must use the `.js` extension (e.g. `import { UserService } from './user.service.js'`), even from `.ts` files.
- **Prisma client is generated into the source tree** at `src/prisma/generated` (gitignored, `moduleFormat = "cjs"`). Import `PrismaClient` from `./generated/client.js`, not `@prisma/client`. Re-run `prisma generate` after any `schema.prisma` change.
- **Prisma 7 driver adapter**: `PrismaService` (`src/prisma/prisma.service.ts`) extends `PrismaClient` and builds a `PrismaBetterSqlite3` adapter from `DATABASE_URL` via `ConfigService`. The datasource URL in `schema.prisma` is intentionally absent; it lives in `prisma7.config.ts` for the CLI.
- **Module wiring**: `ConfigModule` is global and validates the env on boot (`src/config/env.validation.ts`; `DATABASE_URL` and `JWT_ACCESS_SECRET` are required). Feature modules import `PrismaModule` for `PrismaService` (never register `PrismaService` directly).
- **HTTP setup**: `src/app.setup.ts` (`configureApp`) applies `cookie-parser`, the global `ValidationPipe` and `trust proxy`. Both `main.ts` and the e2e helper `test/utils.ts` (`createTestApp`, `resetDatabase`) use it, so e2e tests run with the production pipes.
- **Validation**: the global `ValidationPipe` runs with `whitelist`, `forbidNonWhitelisted`, and `transform`, so DTOs must declare every accepted field with `class-validator` decorators or requests will be rejected. Swagger metadata comes from `@ApiProperty` plus the `@nestjs/swagger` CLI plugin (enabled in `nest-cli.json`).
- **Auth** (`src/auth/`): Passport `local` (login) + `jwt` (access token read from the `access_token` httpOnly cookie, validated without DB). Refresh tokens are opaque, rotated on every `/auth/refresh`, and stored hashed in the `Session` table (`SessionService` is the only stateful part). `JwtAuthGuard` and `ThrottlerGuard` are global `APP_GUARD`s: **every route requires auth unless marked `@Public()`**. In user-owned features, take the owner from `@CurrentUser()` (`{ id }`) and scope every query by it. `UserService` returns the public `AuthUser` shape (`authUserSelect`); only `findByEmail` exposes `passwordHash`, for credential checks. **Pre-registrations**: a `User` with `pending: true` (only `email` + `name` = the nickname; `passwordHash`/`birthDate`/`cep`/`city`/`state` are null only then) is created by a group invitation (`UserService.createPending`); `validateCredentials` rejects it, and `AuthService.register` takes it over on `P2002` (`claimPending`: same id, so memberships and shares stay; sign-up name replaces the nickname), 409 only when the e-mail is really registered.
- **Password change**: `POST /auth/password` (`ChangePasswordDto { currentPassword, newPassword }`, credentials throttle) → `AuthService.changePassword`: `UserService.findCredentialsById` (404 for a pre-registration), **403** on a wrong current password (not 401, so the web's interceptor doesn't refresh), 400 if equal, then `updatePasswordHash`, `SessionService.revokeAllForUser` and a fresh `signIn` (new cookies for this client). E2E in `test/auth.e2e-spec.ts`.
- **Profile** (`src/user/`): `UserController` serves `GET|PATCH /users/me` (always the token's user; 404 for a pre-registration). `UpdateProfileDto` mirrors the sign-up rules with `IsPresent` (no `null`), the address (`cep`/`city`/`state`) is all-or-none, e-mail/password aren't accepted. `UserService.findProfile`/`updateProfile` (`profileSelect`, `toProfile` formats `birthDate` as `YYYY-MM-DD`; an empty patch only reads, since SQLite matches no row on an empty update). E2E in `test/users.e2e-spec.ts`.
- **Observability**: `@nestjs/observe` is set up in `app.module.ts` with placeholder credentials (`YOUR_APP_KEY`/`YOUR_APP_SECRET`) and passed as `instrument` to `NestFactory.create`.
- **Budget** (`src/budget/`): `CategoryGroup` (type, with `kind` INCOME/EXPENSE; optional `goalPercent` 1–100, expense only) → `Category` (just a name) → `Transaction` (a "lançamento": `month` `YYYY-MM`, optional `description` and `dueDay` 1–31, `plannedCents >= 0`, `realizedCents` null while pending, optional `seriesId` shared by the occurrences of one recurring launch; several per category and month). The INCOME/EXPENSE level is the fixed enum, never editable. User-owned tables carry a denormalized `userId` so every query is scoped by it. `User.initialBalanceCents` feeds the opening balance. Default categories are created once, lazily on the first `GET /budget/categories`, guarded by `User.budgetSeeded` (deleting every type must not recreate them). `BudgetService` handles the tree read, the grid and the summary: `GET /budget/entries` returns per-category/month sums of the **effective** amount (`realizedCents ?? plannedCents`) plus `count` and `groupCents`; the grid's editable level is the **launch row** (`GET /budget/lines`: one row per `seriesId`, or per plain transaction, with its cells; `anchorId` = lowest id in the range). `PUT /budget/lines` (`{ cells: [{ anchorId, month, amountCents }] }`) updates the month's transaction, deletes it with 0, or creates a new occurrence copying the anchor (a plain launch gets a new `seriesId`); 404 for another user's anchor, 400 writing to an inactive category (deleting is allowed). The summary sums the **effective** amount (`realizedCents ?? plannedCents`). `TransactionService`/`TransactionController` (`/budget/transactions`) list a month (with `series: { index, count, firstMonth, lastMonth }` and `ownDueDay`), create (`repeatMonths` 1–60 → one per month sharing a `seriesId`), update/delete with `scope` `ONE`|`FOLLOWING` (FOLLOWING also reaches the later, still pending occurrences of the series), set/clear the realization and `PUT /:id/series` (`{ untilMonth }`: extends with pending copies of the last occurrence or deletes the pending ones after it; 409 if a realized one would go, 400 past 60 months or before the first). `series.ts` holds the pure `seriesPositions` (shared by the personal, group and group-statement services) and `planSeriesEnd`. `assertWritableCategories` (`category-access.ts`) is the shared 404/400 ownership-and-active check; `CategoryService`/`CategoryController` create/edit/delete types and categories (409 on duplicate names). Types and categories have `active`: inactive ones keep counting in totals (history kept) but `PUT /budget/lines` and creating/editing/extending transactions reject them with 400 (realizing and deleting still work). Deletes cascade to values. Pure balance math lives in `balance.ts`. **Group shares in the budget**: a `GroupMember` may link its own `expenseCategoryId`/`incomeCategoryId` (`PUT /groups/:id/link`, `SetNull` on category delete); `group-shares.ts` (`linkedShareCells`) reads the user's `GroupTransactionShare`s (former memberships included) **at read time** and adds them to `GET /budget/entries` as `groupCents` (not in `amountCents`) and to the summary; nothing is copied into `Transaction`. `GroupStatementService` (`GET /budget/group-statements?month=`, not `/budget/groups`, which is the category types) returns each group from the user's side (shares, paid, net, transfers involving them, items with the linked category and the effective `dueDay`: for expenses the member's linked payment method's day wins, items ordered by it; left groups as `active: false` while the month has their shares). `isUniqueViolation` (`src/prisma/errors.ts`) detects Prisma `P2002`.
- **Groups** (`src/groups/`): `FinanceGroup` → `GroupMember` (`role` OWNER/MEMBER, soft-ended with `leftAt`; accepting a new invitation reactivates the same row) → `GroupInvitation` (PENDING/ACCEPTED/DECLINED/CANCELED, invitee looked up with `UserService.findPublicByEmail`, which also returns `pending`; an unknown e-mail needs `nickname` (400 `Nickname required for an unregistered e-mail`) and becomes a pre-registration; a pending user joins right away, the invitation stored as ACCEPTED; responses carry `status` and `invitee.pending`, members carry `pending`), `SplitMethod` + `SplitMethodShare` (`type` EQUAL/PERCENT/WEIGHT/FIXED; `value` is ignored/basis points (100% = 10000)/weight/cents; **EQUAL without shares = every active member**; the default "Igualitário" rule is created with the group) and `GroupTransaction` + `GroupTransactionShare` (shares are a **snapshot** stored with each transaction and always add up to `amountCents`; paid ones never change, but **unpaid ones follow the group** via `resplitPending` (`resplit.ts`): editing a rule's type/shares re-divides every unpaid transaction using it (a FIXED rule also sets `amountCents` to its total), and joining/leaving re-divides unpaid ones from `currentMonth()` (`budget/month.ts`) on; when the item's rule is gone/inactive the former members' shares go to the remaining participants in proportion (`redistribute` in `split.ts`), or EQUAL among active members if nobody is left; `GroupTransactionShare.settledAt` = whoever receives the money confirmed the share was paid back (expense: the payer; income: the share's member; `receiverOf`), set via `POST /groups/:id/settlements` (`{ items: [{ transactionId, memberId }], settled }`, all or nothing: 404 outside the group, 400 pending item or the payer's own share, 403 not the receiver); changing the payer, unpaying or re-dividing (`PATCH` amount/rule) an item with confirmed shares is 409 `Undo the confirmed shares first`; `paidByMemberId` null = pending; optional `dueDay` 1–31 (copied to every occurrence and to series extensions, FOLLOWING propagates it, `null` clears it; the month list is ordered by it, undated last); `seriesId`/`scope` like personal transactions, FOLLOWING reaches later unpaid ones; with `repeatMonths` only the first occurrence keeps the payer; `PUT /groups/:id/transactions/:txId/series` extends with unpaid copies keeping the shares snapshot, or deletes the unpaid ones after `untilMonth`, 409 if a paid one would go). Every route goes through `assertMember` (`group-access.ts`: active membership or **404**; `assertOwner` adds 403 for non-owner members). `split.ts` (`computeShares`, largest remainder with ties to the lowest member id; `validateRule`) and `settlement.ts` (`computeGroupBalance`: per member share/paid/received/net, nets add up to zero, only paid items count and settled shares leave both sides; `suggestTransfers`; `isShareSettled(paidByMemberId, share)` = the member paid it or the share is confirmed, which is the `paid` of the user's items in group statements and invoices, next to `groupPaid`) are pure. `GET /groups/:id/balance` also returns `settlements` (other members' shares of paid items with `settled`/`canSettle`). `membership.ts`: `endMembership` handles leave/removal (last member out deletes the group, the oldest member inherits ownership, EQUAL/WEIGHT rules drop the member and PERCENT/FIXED rules naming them turn `active: false` (inactive rules can't be used until edited), then `resplitPending`); `includeInRules` runs on every join (accept and pre-registration, inside an interactive transaction in `InvitationService.join`): adds the member to EQUAL rules with explicit participants and to WEIGHT rules (value 1), turns back on the ones off for being empty, then `resplitPending`. E2E specs that depend on the current month mock `currentMonth` with `vi.mock('../src/budget/month.js', ...)`. E2E helpers: `signUp`/`userBody` in `test/utils.ts`, `createGroup`/`addMember`/`splitMethods` in `test/groups.ts`.
- **Payment methods** (`src/payment-methods/`, `PaymentMethodsModule`, imports `BudgetModule` for the exported `TransactionService`): `PaymentMethod` (`type` CREDIT_CARD/ACCOUNT/OTHER, optional `dueDay`, `active`, unique name per user). `Transaction.paymentMethodId` (expenses only, 400 on an income; `SetNull` on delete) overrides the due day: `TransactionDto` carries `paymentMethod` and the **effective** `dueDay` (`paymentMethod.dueDay ?? transaction.dueDay`), which also orders the statement; FOLLOWING propagates it. `GroupMember.paymentMethodId` (set via `PUT /groups/:id/link`, optional there: omitted keeps it, `null` clears) puts the user's **expense shares** in that method's invoice, read at read time (former memberships too). An invoice is the method's transactions of a month (no closing day) plus those shares: `GET /payment-methods?month=` (each with `invoice` totals), `GET /:id/invoice?month=`, `GET /:id/invoices?from=&to=` (≤ 24 months), `PUT|DELETE /:id/invoice/payment?month=` (realize every pending transaction at its planned amount / back to pending; shares follow their group). `assertUsablePaymentMethod` (`payment-method-access.ts`: 404 not the user's, 400 inactive; keeping an inactive one on edit is fine) is shared with `TransactionService` and `GroupService.setLink`. Pure totals and `dueDate` (clamped to the month's last day) in `invoice.ts`. E2E helper: `createPaymentMethod` in `test/utils.ts`.
- Feature modules follow the Nest CLI resource layout (`<feature>/{module,controller,service}.ts`, `dto/`, `entities/`); generate new ones with `nest g resource`.

## Web architecture

- **Imports**: use the `@/` alias for `src/` (no `.js` extensions; bundler resolution).
- **Atomic design** under `src/components/`, each layer with an `index.ts` barrel. A layer may only import from layers below it: `ui` → `atoms` → `molecules` → `organisms` → `templates` → `routes`.
  - `ui/`: shadcn components, vendored via the CLI. Don't hand-edit beyond theming; build on top of them instead. They import `cn` from the `cn` package (shadcn's clsx + tailwind-merge replacement); app code uses `@/lib/utils`.
  - `atoms/` (e.g. `MoneyText`, `Spinner`, `Logo`, `DueDayBadge` — the "05" due-day chip used by every row that shows a due day; `CheckButton` — the small green ✓ square toggle (`aria-pressed`), solid when pressed, colored by the `--success` token; `FormDialogContent` — **use it instead of `DialogContent` in every form dialog**: one `minmax(0,1fr)` track, `overflow-wrap:anywhere`, `fieldset`/native selects capped, scrolls past the screen height with a sticky opaque footer, `size` `sm`|`md`), `molecules/` (`FormField`, `EmptyState`), `organisms/` (`AppSidebar`), `templates/` (`AppLayout`, `AuthLayout`).
  - The authenticated shell (`AppLayout`) is fluid (no max-width container; `SidebarInset` has `min-w-0` so wide content such as the budget grid scrolls inside instead of widening the page) with a collapsible shadcn `Sidebar` (`collapsible="icon"`, state kept in the `sidebar_state` cookie) with a `UserMenu` (Editar perfil / Alterar senha / Sair) in its footer. Register new top-level pages (Dashboard, Extrato, Grupos, Meios de pagamento) in the side menu via `appNavItems` in `src/lib/navigation.ts`. Sign-out logic lives in `useSignOut()` (`src/features/auth/hooks.ts`).
  - `src/hooks/` holds shared hooks (`useIsMobile`, adapted from shadcn to `useSyncExternalStore`). `src/test/setup.ts` polyfills `matchMedia`, pointer capture and `scrollIntoView` for the sidebar and Radix menus in jsdom.
  - Pages are route files in `src/routes/`. Spec files there are excluded from the route tree via `tsr.config.json`. `src/routeTree.gen.ts` is generated.
- **Data**: `src/lib/api/client.ts` exports the `api` Axios instance (`baseURL` = `VITE_API_URL` or `/api`, `withCredentials`). Its interceptor refreshes the session once on a `401` (single-flight `POST /auth/refresh`, then replays the request) and rejects with `ApiError { status, messages }`, which normalizes Nest's `message: string | string[]`. Auth state comes from `authQueries.me()` (`src/features/auth/`); the `_app` layout route guards internal pages. Each resource lives in `src/features/<feature>/{types,api,queries}.ts`; `queries.ts` exposes `queryOptions` factories (e.g. `userQueries.all()`) shared by `useQuery` and route loaders (`context.queryClient.ensureQueryData(...)`; the router context carries `queryClient`).
- **Money**: render cents with `formatCents` / `<MoneyText cents={...} />`; never convert to floats for math. Parse user input with `parseMoneyInput` (`src/lib/money.ts`, string-based, returns cents or `null`) and show it in inputs with `formatAmount`; `<MoneyInput>` (atom) wires this up.
- **Groups in the personal budget**: `budgetQueries.groupStatements(month)` (under `budgetQueries.all()`) feeds the `GroupStatementsCard` organism on the dashboard and the statement (`detailed`) and `buildStatement(transactions, groupOrder, groupStatements)`, which puts linked shares (`linkedShares`) into their category's type as read-only `shares` (paid = realized). `useBudgetDraft` adds `groupCents` to the shown value and locks those cells (`hasGroupShare` for the tooltip). The link is edited with the `GroupLinkDialog` molecule (`statementLink` in `features/groups/link.ts`; `useGroupActions().setLink`). Group mutations that change shares or memberships also invalidate `budgetQueries.all()`. Fixtures: `stubBudgetApi({ groupStatements })`, `makeGroupStatement`/`makeStatementItem` (`src/test/budget.ts`); specs in `index.groups.spec.tsx`, `extrato.groups.spec.tsx`, `grupos/$groupId.link.spec.tsx`.
- **Budget / dashboard** (`src/features/budget/`, route `src/routes/_app/index.tsx`): months are `YYYY-MM` strings (`months.ts`). Rows go section → type → category (collapsed by default) → **launch rows** (`budgetQueries.lines`, one per series or plain launch). Values are typed on launch rows: the draft (`draft.ts` reducer over keys `anchorId:month`, `useBudgetDraft(lines, entries)`; `savedValues` is the **effective** amount, so realized months show `realizedCents` and every total/goal/balance follows; `isRealized` cells are read-only links to the statement and the fill actions skip them) sends only real changes via `PUT /budget/lines` and blocks navigation while dirty (`useUnsavedChangesGuard`); `forget` takes the anchors of categories that were inactivated or deleted. `buildBudgetTable(groups, lines, months, { line, groupShare }, opening)` (`rows.ts`) sums lines plus group shares (`entries.groupCents`, shown as a read-only "Rateios de grupos" row) into categories and keeps inactive rows (they count); `BudgetGrid` hides them unless "Mostrar inativas". Row menus emit a `GridAction`; the page maps it to `useCategoryActions`/`useCategoryToggle` (`hooks.ts`), to a `BudgetDialog` (`BudgetDialogs`, which takes minimal `DialogGroup`/`DialogCategory` shapes) or to a `LineDialog` (`BudgetLineDialogs`: new launch saved right away through `useTransactionActions`, edit/delete with `FOLLOWING` from `lineTarget(line)`, the first pending month in the window). Goals per expense type come from `buildGoalsOverview` (`goals.ts`, integer math, `GoalsPanel`). The initial balance is saved through `useInitialBalance()` (`hooks.ts`, invalidates every month's summary), used by `BalanceSummary` on the dashboard and the **Saldo inicial** button of the statement (`InitialBalanceDialog`). Specs that land on `/` must `vi.mock('@/features/budget/api')` and call `stubBudgetApi({ lines, shares })` from `src/test/budget.ts` (entries are derived with `entriesOf`; use `makeGroup`/`makeCategory`/`makeLine` for fixtures; `budgetLines` are Aluguel 101, Mercado 201, an unnamed Lazer 301 and Salário 401); launching from the grid also needs `@/features/transactions/api` and `@/features/payment-methods/api` mocked. Category and goal flows live in `index.categories.spec.tsx` and `index.goals.spec.tsx`.
- **Statement** (`src/features/transactions/`, route `src/routes/_app/extrato.tsx`, `?month=YYYY-MM` search param defaulting to the current month): `transactionQueries.month(m)` is keyed under `budgetQueries.all()`, so `useTransactionActions` (`hooks.ts`) invalidating that prefix refreshes the statement, the grid and the summary. The recurring badge is the `SeriesBadge` molecule; clicking it opens `SeriesRangeDialog` (extend/shorten via `useTransactionActions().setSeriesEnd`, also in groups through `useGroupTransactionActions(id).setSeriesEnd`). The **Categorias** button opens the `CategoryManager` organism (a `Sheet` with the tree) reusing `BudgetDialogs` and `useCategoryToggle`. `TransactionFormDialog` has the launch's own due day (`ownDueDay`; sent on edit only when it changed). `buildStatement(transactions, groupOrder)` (`statement.ts`) splits by kind, then by type (`groups`, ordered by the tree's group ids, keeping the server's due-day order inside each) and totals planned/realized/pending/effective. `StatementList` renders Receitas above Despesas in one column, one list per type; `StatementSummary` is a single compact card (items are `role="group"`). `RowActions` keeps its "⋯" visible on touch screens (`pointer-coarse`). - **Groups** (`src/features/groups/`, routes `src/routes/_app/grupos/index.tsx` and `grupos/$groupId.tsx` with `?tab=lancamentos|balanco|membros|rateio&month=YYYY-MM`): `groupQueries` keys everything of a group under `detail(id)` (`['groups', id, ...]`), so the hooks (`useGroupActions`, `useInvitationActions`, `useSplitMethodActions(id)`, `useGroupTransactionActions(id)`) invalidate that prefix; `invitationQueries.received()` is `['invitations']`. Shares carry `settled`; the user's group items (`GroupStatementItem`, `InvoiceShare`) carry `paid` (their share is done) and `groupPaid`, shown as pendente / "A acertar com X" / pago. `useSplitMethodActions` also invalidates the budget (editing a rule re-divides pending shares). `GroupTransactionFormDialog` has the due day (sent on create only when set, on edit only when it changed). - **Payment methods** (`src/features/payment-methods/`, routes `src/routes/_app/meios-de-pagamento/index.tsx` and `$methodId.tsx`, both `?month=YYYY-MM`): `paymentMethodQueries` is keyed **under `budgetQueries.all()`**, so every transaction/group invalidation refreshes invoices and `usePaymentMethodActions` invalidates the whole budget. Forms get the methods through `usePaymentMethodOptions(month, enabled)` (fetched only while the dialog is open); `PaymentMethodSelect` (molecule) is used by `TransactionFormDialog` (expenses only) and `GroupLinkDialog`. `TransactionDialogs` sends `paymentMethodId` on create only when set and on edit only when it changed. The statement row is the `TransactionRow` molecule (shared by `StatementList` and the `PaymentMethodInvoice` organism; shows `t.dueDay` and a method badge linking to the invoice). `knownPaymentMethodMessage` (`errors.ts`) is reused by the transaction and group error helpers. Specs mock `@/features/payment-methods/api` and use `stubPaymentMethodsApi`/`makePaymentMethod`/`makeSummary`/`makeInvoice` from `src/test/payment-methods.ts`; flows in `meios-de-pagamento/*.spec.tsx` and `extrato.payment-methods.spec.tsx`.
- **Profile** (`src/features/profile/`, route `src/routes/_app/settings/profile.tsx`): `profileQueries.me()` (`['profile']`), `useUpdateProfile()` (sets `profileQueries.me()` and `authQueries.me()` so the side menu name changes at once, invalidates groups, invitations and budget). The `ProfileForm` organism sends only changed fields (address as a block) and validates with `validatePersonalData` (`features/auth/register-validation.ts`, shared with `validateRegister`). CEP → city/UF lives in `useCepAddress(saved?)` (`features/address/hooks.ts`; the saved CEP isn't looked up) rendered by the `AddressFields` molecule, both shared with `SignupForm`. Specs that navigate to the profile mock `@/features/profile/api`. Specs that navigate to it must include `changePassword` in the `@/features/auth/api` mock.
